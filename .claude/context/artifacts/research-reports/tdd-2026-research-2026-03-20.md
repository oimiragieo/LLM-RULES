## Detailed Findings

### Topic 1: TDD with AI-Assisted Development (2026 State of Art)

**Key Insights:**

- **TDD prevents AI hallucination exploit**: The dominant 2026 failure mode for AI coding agents is "writing tests that verify broken behavior" — the agent writes code first (wrong), then writes tests confirming the wrong code. TDD's RED-first requirement eliminates this class of bug entirely.
- **Failing test output IS the specification**: The consensus across multiple 2026 sources is that verbatim failing test output (not prose description) should be the specification injected into agent prompts. This is the "Test-Driven Prompting" (TDP) pattern — already in our TDD skill v1.3.0.
- **Agent-specific remediation loops**: Research shows LLM code generation benefits from feedback loops where failing tests are re-injected until passing. Our skill documents this (max 3 repair loops).
- **TDD enables faster AI-assisted development** (not slower): 2026 data shows TDD with AI is faster than free-form AI coding because it constrains the implementation space and eliminates debugging time.
- **Quality as the #1 barrier to AI agent deployment**: 32% of organizations cite quality as top blocker to production agent deployment (LangChain State of Agent Engineering 2025). TDD directly addresses this.

**Current Internal Coverage**: STRONG. TDP, repair loops, multi-agent decomposition (qa/developer/reflection), TDAID phases — all present and current.

### Topic 2: Property-Based Testing

**Key Insights:**

- **fast-check 3.x (2025) improvements**: fast-check now includes improved unicode, date, bigint, and url arbitraries. The `@fast-check/vitest` integration makes adoption frictionless for Vitest projects.
- **Property testing for AI agent invariants**: 2026 best practice is to test *properties* of agent pipelines (routing returns a valid agent type for any input; memory serialization is always reversible), not just specific cases.
- **Coverage gap with deterministic tests**: Property-based tests catch edge cases invisible to example-based tests. Mutation testing confirms the tests are exercising real logic.

**Current Internal Coverage**: GOOD. The skill has 4 fast-check examples (routing, memory, hook, path), uses `fc.jsonValue()`, and references `@fast-check/vitest`. No gaps identified.

### Topic 3: Mutation Testing (Stryker + Vitest)

**Key Insights:**

- **Stryker 7.0 officially supports Vitest** (2025). StrykerJS 7 adds Vitest runner alongside Tap, replacing Jest as the recommended runner for ESM/TypeScript projects.
- **Vitest Browser Mode NOT supported in Stryker** (as of v7-v9): GitHub issue #4557 is open. Stryker v9.0.1 adds partial browser mode setup, but full support is not confirmed. Our skill's LIMITATION NOTE about this is accurate.
- **Mutation score targets**: 80% is the industry recommended threshold for security-critical code. Agent Studio skill uses this correctly.
- **AI-agent workaround for browser mode**: When Stryker browser mode fails, AI agents can simulate mutation testing by manually introducing mutations and checking test outcomes. This is emerging as a practical pattern.
- **node:test + Jest runner**: For CJS projects using `node --test`, the `@stryker-mutator/jest-runner` fallback is still the right approach. Our skill documents this.

**Current Internal Coverage**: STRONG. The skill documents both Vitest and CJS configurations, incremental mode, thresholds, and limitations accurately.

### Topic 4: AI Output Evaluation and Non-Deterministic Agent Testing

**Key Insights (external research confirms gap):**

- **Binary pass/fail assertions are insufficient for LLM outputs**: Every 2026 source confirms this. LLM outputs need score-based evaluation.
- **LLM-as-judge pattern**: Use a separate LLM to evaluate agent output quality. This pattern appears in tools like Braintrust, PromptFoo, and Arize Phoenix. Currently **not integrated into our TDD skill** beyond the score-based assertion pattern.
- **Tool-call sequence validation**: Validating the sequence and count of tool calls (not just final output) is the 2026 standard for agent correctness testing. Our skill documents this pattern.
- **Snapshot testing for agent structure**: Capture and assert on output *shape* (not content) — `.toMatchObject({ status: 'success', output: expect.any(String) })`. Our skill has this in `testing.md` but not in TDD SKILL.md itself.

**GAP IDENTIFIED**: The TDD skill does not reference `Skill({ skill: 'agent-evaluation' })` for LLM-as-judge workflows. The `testing.md` rules file mentions `Skill({ skill: 'agent-evaluation' })` but the TDD SKILL.md's AI Output Evaluation section does not cross-reference or invoke this skill.

### Topic 5: LSP Pre-RED Verification

**Key Insights:**

- The LSP Pre-RED Type Verification section in the TDD skill is well-documented (use `lsp_hover` to verify API exists before writing the failing test).
- **CJS limitation acknowledged**: The skill notes that for `.cjs` files, fall back to ripgrep if LSP returns empty.
- **LSP navigator skill v1.2.0** is verified current (2026-03-07), with complete operation reference including the diagnostics runner.

**GAP IDENTIFIED**: LSP Pre-RED verification is documented in the TDD skill but is *optional* ("Before writing a failing test, verify..."). External research suggests this should be a *mandatory gate* for any function that already exists in the codebase (to prevent "fails due to wrong API" false reds). The TDD skill should make this explicit: mandatory when modifying an existing API, optional when creating a new function.

### Topic 6: Session-Persistent TDD (ralph-loop / tdd-state.json)

**Key Insights:**

- The internal skill already implements the `tdd-state.json` schema for session-persistent TDD backlogs. This is ahead of external tooling — no 2026 source documents this pattern at the same level of detail.
- **Multi-session TDD resumption**: The ability to resume a TDD backlog after context reset is a significant capability gap in most 2026 agent frameworks.

**Current Internal Coverage**: STRONG and ahead of industry. No gaps.

### Topic 7: Test Runner Selection Matrix

**Key Insights:**

- **Vitest 4.x** (2025-2026) has stable Browser Mode and is the recommended runner for ESM/TypeScript. Boot time ~1.2s vs Jest ~8s.
- **node --test** (built-in) is still the right choice for CJS/CommonJS files without transpilation overhead.
- **Jest deprecation**: Multiple 2026 sources indicate Jest is no longer recommended for new TypeScript projects. Vitest has won.

**Current Internal Coverage**: STRONG. The skill's runner selection table is accurate and complete.

### Topic 8: Contract Testing

**Key Insights:**

- **Consumer-driven contract testing** (Pact.io) is the 2026 standard for microservice and multi-agent pipeline testing. Our skill documents hook boundary contract testing but does not reference Pact for cross-agent contracts.
- **TaskUpdate metadata validation** (processedReflectionIds) is documented and an example contract test pattern is provided.

**GAP IDENTIFIED (minor)**: No mention of Pact.io or consumer-driven contract testing for agent-to-agent API contracts. The current patterns cover hook boundaries and TaskUpdate metadata but not cross-agent message schemas at a broader level.
